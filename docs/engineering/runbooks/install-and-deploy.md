# رانبوک نصب و استقرار (فاز ۰، آیتم 0.10)

این سند می‌گوید **یک نصب تمیز چاپینو چطور بالا می‌آید** - روی XAMPP، روی Laragon، با `php -S`، و
(وقتی هاست واقعی آمد) روی هاست اشتراکی. هر گام دستوری دارد که می‌توان کپی کرد و هر گام یک راه بررسی
دارد که نشان می‌دهد همان گام درست انجام شده است.

دو قاعده‌ی این سند:

1. **هیچ گامی «باید کار کند» نیست؛ هر گام یک راه بررسی دارد.** اگر بررسی جواب نداد، همان‌جا بایستید.
2. **تفاوت «اجرا شده» و «مستند» را می‌نویسیم.** چیزهایی که در محیط توسعه اجرا و تأیید شده‌اند از
   چیزهایی که فقط روی ماشین شما قابل تأیید است جدا آمده‌اند (بخش ۱۱).

اسناد مرتبط: [ADR-0002](../adr/ADR-0002-shared-hosting-target.md) (هدف: هاست اشتراکی)،
[project-context](../project-context.md) (`O-2`, `O-3`, `O-20`)،
[گزارش توانمندی هاست](../../../bin/check-requirements.php) (اسکریپتی که بخش ۱۲ را پر می‌کند).

## ۰) پیش‌نیازها

| نیاز | مقدار | چرا |
| --- | --- | --- |
| PHP | **۸.۱ یا بالاتر** (`O-3`، موقتی) | نسخه‌ی هدف؛ از قابلیتی جدیدتر از کمینه استفاده نمی‌شود |
| افزونه‌ها | `mbstring`, `pdo`, `json`, `curl`, `openssl`, `zip` (+ درایور `pdo_mysql` یا `pdo_sqlite`) | متن فارسی، پایگاه‌داده، درگاه پرداخت، پیامک، بسته‌بندی |
| پایگاه‌داده | MySQL 5.7+/8 یا MariaDB 10.3+ با `utf8mb4` (روی هاست - فرضی تا گزارش هاست بیاید)، SQLite (فقط لوکال) | `O-2` |
| نوشتن‌پذیری | پوشه‌ی `storage/` و زیرپوشه‌هایش | نشست، لاگ، صف، آپلود |
| زمان‌بندی | یک کران روی هاست (بخش ۷) | تنها مکانیزم پس‌زمینه روی هاست اشتراکی (ADR-0006) |
| URL | بازنویسی (`mod_rewrite` یا معادل) | بخش ۲.۴ - روی هر سه سناریوی لوکال فراهم است |

بررسی خودکار همین‌ها روی ماشین شما:

```bash
php bin/check-requirements.php
php bin/check-requirements.php --json > host-facts.json   # خروجی ماشین‌خوان برای بخش ۱۲
```

«الزامی» یعنی نبودش نصب را متوقف می‌کند؛ «اختیاری» یعنی محصول کار می‌کند ولی چیزی (مثلاً `intl`)
کم است؛ «واقعیت» یعنی عددی که فقط ثبت می‌شود (نسخه‌ی PHP، محدودیت آپلود، SSL).

## ۱) چیدمان پوشه‌ها (قاعده‌ی اصلی)

```
chapino/
├── public/          ← تنها پوشه‌ای که وب‌سرور باید سرو کند (document root)
│   ├── index.php    ← تنها فایل PHP اجراشدنی
│   └── assets/      ← CSS، فونت فارسی، اسکریپت پایه
├── app/ bin/ config/ database/ tests/ tools/   ← بیرون از وب‌ریشه
└── storage/         ← وضعیت زمان اجرا (سشن، لاگ، صف، پایگاه‌داده SQLite)
```

- **`document root` باید `public/` باشد.** اگر یک سطح بالاتر تنظیم شود (`htdocs/chapino`)، فایل
  `.htaccess` ریشه همه‌چیز را می‌بندد (fail closed) - ولی سایت هم درست کار نمی‌کند. این تنظیم را
  جدی بگیرید.
- **`storage/` بهتر است بیرون از وب‌ریشه باشد** (روی هاست اشتراکی معمولاً یک سطح بالاتر از
  `public_html`). اگر چنین امکانی نبود، `storage/.htaccess` آن را می‌بندد.
- هیچ فایل تستی داخل `public/` نیست و نباید برود: صفحه‌ی هارنس از طریق مسیر سرو می‌شود، نه فایل.

## ۲) سه سناریوی لوکال

### ۲.۱ XAMPP (ویندوز/مک)

1. پروژه را در `C:\xampp\htdocs\chapino` بگذارید (کل پوشه، نه فقط `public`).
2. `document root` را به `C:\xampp\htdocs\chapino\public` ببرید. دو راه:
   - ساده‌ترین: در `httpd.conf` مقدار `DocumentRoot` و بلوک `<Directory>` را عوض کنید؛
   - بهتر (و باقی‌ماندنی): یک VirtualHost بسازید و `hosts` ویندوز را هم به‌روز کنید:

   ```apache
   <VirtualHost *:80>
       ServerName chapino.test
       DocumentRoot "C:/xampp/htdocs/chapino/public"
       <Directory "C:/xampp/htdocs/chapino/public">
           AllowOverride All          # بدون این، .htaccess خوانده نمی‌شود و همه‌ی مسیرها 404 می‌شوند
           Require all granted
       </Directory>
   </VirtualHost>
   ```

3. مسیر را بدون VirtualHost هم می‌توان امتحان کرد: `http://localhost/chapino/public/`
   (این همان حالت «زیرپوشه» است که تست‌های پروژه پوشش می‌دهند).
4. سرویس‌های Apache و MySQL را در کنترل‌پنل XAMPP روشن کنید (فرضی؛ تا تأیید روی هاست، `O-20`)، بعد بخش ۳ و ۵ را ادامه دهید.

**دام‌های رایج:** `AllowOverride None` (همه‌ی مسیرها 404) · `DocumentRoot` یک سطح بالاتر (همه‌چیز
۴۰۳) · فایل `config/config.php` ساخته‌نشده (پیام خطای فارسی راهنما).

### ۲.۲ Laragon

1. کل پروژه در `C:\laragon\www\chapino`.
2. Laragon به‌طور پیش‌فرض روی پوشه‌ی پروژه VirtualHost خودکار می‌سازد؛ چون وب‌ریشه‌ی ما `public/`
   است، ریشه را به آن بدهید: راست‌کلیک روی پروژه → `www` → یا در `laragon.ini` مقدار
   `DocumentRoot = C:\laragon\www\chapino\public` (یا از منوی Laragon: `Preferences → Document Root`
   را دست نزنید و به‌جایش پوشه‌ی `public` را به‌عنوان ریشه معرفی کنید).
3. سرویس MySQL فرضی را از Laragon روشن کنید و از HeidiSQL دیتابیس بسازید (بخش ۳).
4. آدرس معمول: `http://chapino.test/`.

**دام رایج:** Laragon «Pretty URLs» را در حالت Apache (فرضی) با `mod_rewrite` فعال می‌کند؛ اگر روی nginx
(فرضی) سوییچ کرده‌اید، `try_files` لازم است (بخش ۲.۴).

### ۲.۳ `php -S` (بدون هیچ وب‌سروری)

```bash
php -S localhost:8000 -t public tools/dev/serve-router.php
```

- `-t public` وب‌ریشه را درست می‌کند و `tools/dev/serve-router.php` نقش بازنویسی را بازی می‌کند:
  فایل‌های واقعی را خود سرور می‌دهد و بقیه به front controller می‌رود.
- این فایل **ابزار توسعه** است و هرگز روی هاست کپی نمی‌شود (خودش هم اگر زیر Apache فرضی اجرا
  شود، کار نمی‌کند).
- اگر بدون router اجرا کنید، فقط `/` کار می‌کند و بقیه‌ی مسیرها ۴۰۴ می‌شوند - این ایراد محصول نیست،
  کمبود وب‌سرور است.

### ۲.۴ بازنویسی URL (بدانید و بخواهید)

لینک‌ها و آدرس دارایی‌ها به شکل تمیز ساخته می‌شوند (`/design-system`, `/assets/...`). پس:

- Apache (فرضی): `mod_rewrite` روشن + `AllowOverride All` (یا حداقل `FileInfo`).
- nginx (فرضی): معادلش `try_files $uri /index.php?$query_string;` است.
- **میزبان بدون بازنویسی:** front controller با `/index.php?r=/path` هم پاسخ می‌دهد (سمت ورودی
  پشتیبانی می‌شود و تست دارد)، ولی لینک‌های تولیدشده در قالب تمیز هستند و روی چنین میزبانی
  ناوبری می‌شکند. این یک محدودیت شناخته‌شده است؛ اگر هاست شما بازنویسی ندارد، این را بگویید تا
  حالت URL در همان جا تصمیم و اضافه شود (`O-20`).

## ۳) پایگاه‌داده

### MySQL / MariaDB (فرضی؛ پروفایل هدف `O-2`)

```sql
CREATE DATABASE chapino CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'chapino'@'localhost' IDENTIFIED BY 'یک-رمز-قوی';
GRANT ALL PRIVILEGES ON chapino.* TO 'chapino'@'localhost';
FLUSH PRIVILEGES;
```

`utf8mb4` اجباری است: متن فارسی و ایموجی باید سالم بمانند. کالیشن پیش‌فرض
`utf8mb4_unicode_ci` است.

### SQLite (فقط لوکال و تست؛ فرضی)

هیچ کاری لازم نیست؛ مسیر پیش‌فرض `storage/database.sqlite` است و خودش ساخته می‌شود (فرضی). روی هاست
واقعی از SQLite استفاده نکنید: هدف `O-2` است و پشتیبان‌گیری/همزمانی روی هاست اشتراکی مسئله دارد.

## ۴) پیکربندی

```bash
cp config/config.example.php config/config.php
```

`config/config.php` در مخزن نیست (رمزها و مسیرهای میزبان آنجاست). کلیدهایی که واقعاً مهم‌اند:

| کلید | مقدار در هاست واقعی | چرا |
| --- | --- | --- |
| `app.env` | `production` | صفحه‌های توسعه (`/design-system`, `/tests/browser`) در این حالت ۴۰۴ می‌شوند |
| `app.debug` | `false` | پیام خطای دیباگ می‌تواند اطلاعات داخلی را لو بدهد |
| `app.url` | آدرس واقعی سایت | ساخت لینک مطلق و بازگشت از درگاه پرداخت |
| `app.timezone` | `UTC` | ذخیره‌سازی UTC است؛ ساعت ایران مسئله‌ی نمایش است |
| `storage.path` | مسیر نوشتن‌پذیر | لاگ، سشن، صف، آپلود |
| `database.*` | مقادیر هاست | بخش ۳ |
| `security.session_save_path` | زیرمجموعه‌ی `storage` | نشست‌ها بیرون از وب‌ریشه |
| `logging.level` | `warning` (در تولید) | حجم لاگ |

نکته: اگر با `bin/install.php` نصب کنید، این فایل **خودش نوشته می‌شود** و نیازی به کپی دستی نیست.
کپی دستی برای وقتی است که بخواهید مقادیر را خودتان بدهید.

## ۵) نصب

SQLite (لوکال، فرضی، سریع‌ترین راه دیدن محصول):

```bash
php bin/install.php --driver=sqlite
```

MySQL (فرضی، شکل واقعی):

```bash
php bin/install.php --driver=mysql --host=127.0.0.1 --port=3306 \
    --name=chapino --user=chapino --password='یک-رمز-قوی' \
    --url=https://example.ir
```

نصب‌کننده به ترتیب: (۱) آماده‌سازی `storage/`، (۲) بررسی اتصال پایگاه‌داده، (۳) نوشتن
`config/config.php`، (۴) اجرای همه‌ی مهاجرت‌ها، (۵) مقدارگذاری تنظیمات پیش‌فرض، (۶) بررسی
نیازمندی‌ها. **تا اتصال پایگاه‌داده ثابت نشود هیچ چیزی نوشته نمی‌شود** - نصب نیمه‌کاره بدتر از
نصب نبودن است.

`--force` تنها برای بازنویسی پیکربندی موجود است و `--skip-requirements` گام ۶ را رد می‌کند.

## ۶) بررسی نصب (این چهار دستور را رد نکنید)

```bash
php bin/migrate.php --status     # چه چیزی اعمال شده، چه چیزی در انتظار است
php bin/seed.php --status        # تنظیمات ذخیره‌شده + تفاوت با پیش‌فرض‌ها
php bin/smoke.php                # آیا فرانت‌کنترلر واقعی درست پاسخ می‌دهد
```

و از مرورگر: `GET /api/health` → باید `status: ok` و وضعیت پایگاه‌داده را برگرداند، بدون افشای
رمز، مسیر یا نسخه‌ی کتابخانه‌ها.

در محیط توسعه (`app.env=local`) دو صفحه‌ی ابزاری هم در دسترس است:

- `/design-system` - راهنمای زنده‌ی اجزای رابط.
- `/tests/browser` - هارنس تست مرورگر (`O-11`، گزینه‌ی ۲): همان مواردی را اجرا می‌کند که
  `node tools/dev/browser-tests.mjs` اجرا می‌کند.
- `/maintenance` - ابزار اپراتور برای مهاجرت و تنظیمات پیش‌فرض (بخش ۱۳.۲)؛ با توکن فایل‌سیستم کار
  می‌کند و در حالت تولید هم در دسترس است.

## ۷) کران (بدون آن، صف کار نمی‌چرخد)

هاست اشتراکی cPanel:

```
*/1 * * * * /usr/bin/php /home/USER/chapino/bin/cron.php >/dev/null 2>&1
```

XAMPP/Laragon روی ویندوز: Task Scheduler با همین دستور، هر یک دقیقه.

بررسی این‌که واقعاً اجرا می‌شود:

```bash
php bin/cron.php --status        # وضعیت صف و آخرین ضربان (heartbeat)
php bin/cron.php --limit=50      # اجرای دستی یک بار برای اطمینان
```

اگر «آخرین ضربان» قدیمی است، کران اجرا نمی‌شود - همین یک عدد کافی است تا تشخیص دهید.

## ۸) رفتن به حالت تولید

1. `app.env = production` و `app.debug = false` (بخش ۴).
2. `storage/` را بیرون از وب‌ریشه ببرید (یا حداقل مطمئن شوید `storage/.htaccess` خوانده می‌شود).
3. HTTPS را فعال کنید (پنل هاست) و `app.url` را با `https` بنویسید.
4. صفحه‌های ابزاری را دستی پاک نکنید؛ در `production` هر سه (style guide و هر سه مسیر هارنس) ۴۰۴
   هستند و تست دارد.
5. `php bin/migrate.php --status` و `php bin/smoke.php` را یک بار دیگر بزنید.

## ۹) پشتیبان‌گیری و به‌روزرسانی

```bash
mysqldump -u chapino -p chapino > backup-$(date +%F).sql
tar -czf storage-$(date +%F).tar.gz storage/     # سشن‌ها، لاگ، آپلودها
php bin/migrate.php --status                      # بعد از هر به‌روزرسانی
php bin/migrate.php                               # اعمال مهاجرت‌های جدید (ایمن برای تکرار)
```

مهاجرت‌ها نسخه‌دار و فقط-جلورو هستند؛ `--down` برای عقب‌گرد اضطراری است و `--fresh --force` فقط
روی لوکال (همه‌ی جدول‌ها را پاک می‌کند).

## ۱۰) عیب‌یابی

| نشانه | علت احتمالی | کار درست |
| --- | --- | --- |
| همه‌ی مسیرها ۴۰۴، `/` درست | بازنویسی غیرفعال است | `AllowOverride All` + `mod_rewrite`؛ روی nginx (فرضی) معادل `try_files` |
| همه‌چیز ۴۰۳، یا سایت فقط زیر `/public/` جواب می‌دهد | `document root` یک سطح بالاتر از `public/` است | ریشه را به `public/` بدهید. فایل `.htaccess` ریشه عمداً این درخت را می‌بندد و فقط دو فایل لازم (فرانت‌کنترلر و نصب‌کننده) خودشان را باز می‌کنند؛ این یک تور اطمینان است، نه یک حالت پشتیبانی‌شده - در آن حالت همه‌ی لینک‌های ساخته‌شده اشتباه‌اند |
| صفحه‌ی سفید یا خطای فارسی «فایل پیکربندی پیدا نشد» | `config/config.php` ساخته نشده | `php bin/install.php ...` |
| صفحه بدون CSS و فونت | پیشوند مسیر (زیرپوشه) اشتباه شده یا دارایی‌ها ۴۰۴ می‌دهند | آدرس را با پیشوند باز کنید: `/chapino/public/`؛ لاگ Apache (فرضی) را ببینید |
| `503` با پیام راه‌اندازی | پایگاه‌داده در دسترس نیست یا مهاجرت‌ها اعمال نشده | `php bin/migrate.php --status` و سپس `php bin/migrate.php` |
| «نشست شروع نشد» یا هشدار session | `storage/` نوشتن‌پذیر نیست | مجوز پوشه‌ها را درست کنید (روی لینوکس: کاربر وب‌سرور مالک/گروه) |
| کران هیچ کاری نمی‌کند | دستور کران اشتباه است یا PHP مسیر درست ندارد | `php bin/cron.php --status` و مسیر مطلق `php` را در کران بگذارید |
| اسکریپت‌ها یا فونت‌ها ۴۰۴ | `public/assets/` کامل آپلود نشده | دارایی‌ها را دوباره آپلود کنید؛ `Asset::url` روی فایل نبود، خطا می‌دهد نه ۴۰۴ خاموش |
| `install.php` روی نصب تازه ۴۰۴ می‌دهد | `config/config.php` وجود دارد (نصب انجام شده) | طبیعی است؛ برای نصب دوباره، فایل پیکربندی را از پنل پاک کنید |
| فایل توکن را در پنل نمی‌بینم | پوشه‌ی `storage/` هنوز ساخته نشده یا مجوز ندارد | صفحه را دوباره باز کنید؛ اگر ساخته نشد، مجوز نوشتن پوشه‌ی نصب را در پنل درست کنید |
| پس از وارد کردن توکن درست، باز هم «توکن درست نیست» | نشست PHP کار نمی‌کند (`session.save_path` نانوشتنی) | مسیر ذخیره‌ی نشست را در پنل هاست به پوشه‌ای نوشتن‌پذیر تغییر دهید |

## ۱۱) چه چیزی تأیید شده و چه چیزی نه

| موضوع | وضعیت |
| --- | --- |

## ۱۳) نصب و به‌روزرسانی بدون shell (نصب‌کننده‌ی وب)

اگر روی هاست دسترسی ترمینال ندارید (حالت معمول هاست اشتراکی)، به‌جای گام‌های CLI بالا از دو صفحه‌ی
وب استفاده کنید. هر دو با **توکن یک‌بارمصرف** کار می‌کنند و هیچ‌کدام توکن را روی صفحه چاپ نمی‌کنند.

### ۱۳.۱ نصب از مرورگر (`public/install.php`)

1. آدرس `https://your-site/install.php` را باز کنید (زیرپوشه هم کار می‌کند:
   `https://your-site/chapino/public/install.php`).
2. صفحه یک فایل توکن می‌سازد: `storage/install-token.php`. مقدار داخل آن را از **فایل‌مدیر پنل هاست**
   باز کنید و در کادر بگذارید. اگر فایل را نمی‌بینید، صفحه را دوباره باز کنید تا ساخته شود.
   این مرحله همان اثبات دسترسی شما به فایل‌های سایت است؛ بدون آن، هر کسی که آدرس را باز کند
   می‌توانست نصب را به نام شما انجام دهد.
3. پس از تأیید توکن، **گزارش توانمندی هاست** نشان داده می‌شود (الزامی / اختیاری / واقعیت). اگر
   موردی «الزامی» برقرار نباشد، دکمه‌ی نصب کار نمی‌کند و گزارش می‌گوید چه چیزی را در پنل درست کنید.
4. مقادیر پایگاه‌داده را وارد کنید (همان بخش ۳) و «نصب کن» را بزنید. نصب‌کننده به ترتیب:
   پوشه‌های نوشتنی → بررسی نیازمندی‌ها → آزمایش اتصال پایگاه‌داده → همه‌ی مهاجرت‌ها → تنظیمات
   پیش‌فرض → **و در آخر** نوشتن `config/config.php`.
   ترتیب مهم است: تا وقتی پرونده‌ی پیکربندی نوشته نشده، این صفحه زنده می‌ماند. اگر جایی وسط کار
   قطع شوید، دوباره همان صفحه را باز می‌کنید و نصب ادامه پیدا می‌کند (مهاجرت‌ها تکراری‌شدنی و
   تنظیمات فقط-ایجاد هستند).
5. صفحه‌ی موفقیت، خط کران و گام‌های بعدی را نشان می‌دهد. از این لحظه `config/config.php` وجود دارد،
   پس خود صفحه‌ی نصب برای همه **۴۰۴** می‌دهد (خودغیرفعال) و توکن هم مصرف (پاک) شده است.

### ۱۳.۲ به‌روزرسانی بعدی (`/maintenance`)

برای اعمال مهاجرت‌های تازه یا افزودن تنظیمات پیش‌فرض جدید روی همان هاست:

1. `/maintenance` را باز کنید؛ اگر توکنی وجود نداشته باشد، ساخته می‌شود.
2. مقدار `storage/install-token.php` را از فایل‌مدیر بردارید و در فرم بگذارید.
3. یکی از کارها را انتخاب کنید:
   - **اعمال مهاجرت‌ها** — همه‌ی مهاجرت‌های در انتظار را اجرا می‌کند و توکن را مصرف می‌کند.
   - **افزودن تنظیمات پیش‌فرض تازه** — فقط کلیدهای غایب را اضافه می‌کند؛ مقدارهای دست‌کاری‌شده‌ی
     شما دست‌نخورده می‌ماند (سرشت فقط-ایجاد).
   - **قفل کردن** — بدون اجرای کاری، توکن را می‌سوزاند.
4. هر کار در لاگ ثبت می‌شود («چه کسی، چه زمانی»). توکن یک‌بارمصرف است: پس از هر کار، صفحه دوباره
   قفل می‌شود و برای کار بعدی یک توکن تازه لازم است.

تفاوت `/maintenance` با ابزارهای توسعه (`/design-system` و `/tests/browser`) عمدی است: آن دو در حالت
`production` چهارصدوچهار می‌شوند، چون ابزار توسعه‌اند. `/maintenance` **ابزار اپراتور** است و روی هاست
واقعی باید در دسترس بماند؛ محافظش توکن فایل‌سیستم + CSRF + شمارش تلاش + لاگ است، نه حالت محیط.

### ۱۳.۳ نکات امنیتی همین مسیر

- توکن ۶۴ کاراکتر هگز است، در `storage/` (بیرون وب‌ریشه) می‌نشیند، و فایلش PHP است تا در بدترین
  حالت (سرو شدن پوشه‌ی storage توسط وب‌سرور) مقدارش به مرورگر نرسد.
- خواندن توکن با تجزیه انجام می‌شود، نه با اجرای فایل: اگر کسی چیزی به آن فایل اضافه کند، نادیده
  گرفته می‌شود (تست دارد).
- پنج تلاش ناموفق برای هر بازدیدکننده، آن را ۱۵ دقیقه قفل می‌کند (شمارنده‌ی فایلی، چون پایگاه‌داده‌ای
  وجود ندارد که بشمارد).
- رمز پایگاه‌داده هرگز در HTML برنمی‌گردد (نه در فرم، نه در پیام خطا).
- اگر `config/config.php` وجود داشته باشد، صفحه‌ی نصب برای همه ۴۰۴ است - پس نیازی نیست فایل را پاک
  کنید؛ ولی اگر خواستید، پاک‌کردنش بی‌خطر است.
